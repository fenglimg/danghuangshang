# OpenProse：频道回流模式（Channel Feedback Mode）

## 结论
在当前 danghuangshang + OpenClaw 环境里，OpenProse 更适合作为**公开流程编排层**，而不是“私有 transcript 汇总层”。

推荐模式：
- OpenProse 负责：流程定义、步骤编排、角色分工、输出格式约束
- 子 agent 负责：把执行结果**直接发回当前 Discord 频道/线程**
- 司礼监负责：基于频道内公开回执做收口与二次调度

## 为什么选这个模式
当前验证里，内部 transcript / tool-result 回流会碰到几类现实问题：
- `sessions_history` / agent-to-agent history 策略限制
- `sessions_spawn(runtime=subagent)` 与 `streamTo` 的兼容问题
- 不同 OpenClaw 版本/打包产物下，回流逻辑存在实现差异

而“频道回流模式”有几个优势：
- 与三省六部的**公开流转**原则一致
- 不依赖隐藏 transcript 聚合
- 出问题时更容易人工接管
- 更适合把 runbook / demo /模板快速固化

## 适用场景
适合：
- triage（需求拆解与拟派单）
- review（代码审查结论公开回帖）
- release（发布检查清单/公告草稿回帖）

不适合：
- 依赖私有中间态的复杂多轮内部编排
- 强依赖流式回传到父流程的场景
- 需要“黑箱式后台自动汇总”的工作流

## 工作方式
### 旧模式（人肉对话推进）
1. 司礼监接任务
2. 手工判断派给谁
3. 等回复
4. 再手工推进下一步
5. 最后手工汇总

### 新模式（OpenProse + 频道回流）
1. 司礼监触发一个 OpenProse workflow
2. Workflow 负责拆步骤与约束格式
3. 子 agent 完成后直接在当前线程回帖
4. 司礼监根据公开回帖做最终收口/汇总

## 对三省六部的意义
这不是把司礼监替换掉，而是把司礼监从“逐轮人工推进者”升级为：
- 流程设计者
- 规则制定者
- 结果审阅者

换句话说：
- 以前：你亲自调度
- 现在：你设计流程，让流程调度，并在频道里留下公开足迹

## 落地建议
### 第一阶段
- 先做 smoke：子 agent 回频道一条 `OpenProse smoke OK`
- 验证线程/频道回流模型是通的

### 第二阶段
把三个 demo 迁移到统一模式：
- `triage.prose`：输出拟派单草稿并回帖
- `review.prose`：输出审查清单并回帖
- `release.prose`：输出发布清单/公告草稿并回帖

### 第三阶段
在 docs 中沉淀：
- 哪些任务适合 OpenProse
- 哪些仍然适合人肉调度
- 回帖格式标准
- 失败时如何人工接管

## 风险与边界
- 不要把它当成“内部黑盒总控器”
- 不要在未确认回帖目标前做高风险自动动作
- 不要默认依赖内部 history / streamTo 机制

## 当前判断
如果目标是“减少频繁对话推进的人肉调度成本”，OpenProse **值得继续推进**，但要明确采用：

**OpenProse = 流程编排层**  
**频道消息 = 公开回流层**
